# Issue の起票・修正

記事のネタを Issue にする手順。過去の Issue と並べて読めるよう構成を揃える。
PR 側の規約は `write-pr` スキルに揃えてある。両者で表記がぶれないようにする。

対象リポジトリは `hot377/tech-blog`。

## 手順

1. **テンプレートを読む**

   ```bash
   cat .github/ISSUE_TEMPLATE/article.md
   ```

   **見出しと各セクションの書き方はテンプレートが唯一の情報源。**
   このスキルで見出しを再定義しない（二重管理を避けるため）。

   - 見出しを増やしたり減らしたりしない
   - 埋まらないセクションは空欄で出さず、ユーザーに材料を確認する
   - 案内用の HTML コメントは、埋めたら削除する

2. **一次情報で裏付けを取る**

   WebSearch で候補を探し、**WebFetch で実際にアクセスして内容を確認する。**
   URL を推測で書かない。要約記事や伝聞ではなく、次を優先する。

   | 一次情報 | そこで確認できること |
   | --- | --- |
   | 公式ドキュメント | 設定項目、制約、必要な権限 |
   | What's New、公式ブログ | 発表日、変更の概要、対象範囲、料金 |
   | リリースノート、CHANGELOG | 実装されたバージョンと時期。「いつから使えるか」の特定に使う |
   | ソースコード、Issue、RFC | ドキュメントに書かれていない挙動 |
   | イベントの公式ページ、セッション資料 | 開催日、登壇者、発表内容 |

   発表（What's New）とリリースノートは日付がずれることがある。
   読者の再現性に関わるため、必要バージョンが特定できる場合は本文に書く。

   裏付けの過程でユーザーの認識と一次情報がずれていたら、
   **黙って直さずに、ずれている点を明示して伝える。** そのうえで正確な表現を本文に反映する。

3. **重複を確認する**

   ```
   mcp__github__list_issues (state 指定なしで全件を見る)
   ```

   `search_issues` は意味検索のため既存 Issue を取りこぼすことがある。これだけに頼らない。
   同じネタの Issue が既にあれば、新規起票せず手順7の修正に切り替える。

4. **タイトルを決める**

   日本語で、記事の内容ではなく**やること**を書く。`Issue:` などのプレフィックスは付けない。

   - 良い例: `CloudWatch agent の journald ログ収集対応を検証して記事にする`
   - 良い例: `IAM ロールの管理ポリシー上限が 20 になった件を Terraform で検証して記事にする`
   - 避ける: `記事執筆: CloudWatch agent が journald ログ収集をネイティブサポート`

5. **ラベルを決める**

   ラベル一覧を取得する MCP ツールは無い。既存の使用実績から引く。

   ```
   mcp__github__list_issues / list_pull_requests の labels フィールドを見る
   ```

   命名規則は `aws/<サービス名>`、`tech/<技術名>`、`ai/<領域>`、`ci/cd` など。
   付ける前に `mcp__github__get_label` で存在を確認する。
   **存在しないラベルを勝手に作らない。** 新設が必要ならユーザーに提案して判断を仰ぐ。

6. **起票する**

   ```
   mcp__github__issue_write (method: create)
   ```

7. **修正する場合**

   `issue_read`(method: `get`)で現在の本文を取得してから `issue_write`(method: `update`)で更新する。
   更新後は、何をどう変えたかを表で報告する。

## 注意

- 本文に絵文字を使わない
- チェックボックスは起票時点では未チェック（`- [ ]`）。検証が済んだ時点で `- [x]` にする
- 起票済みの Issue のタイトル・見出し構成を、理由なく変えない
- 即着手して即完了するリポジトリ改善タスク（テンプレート整備など）は、Issue を立てず PR だけで済ませる。
  Issue にする価値があるのは、記事のネタのストックと、後回しにする改善タスク
