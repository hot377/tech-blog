## はじめに

皆さんは AWS のアップデート情報を追っていますか？

AWS のアップデートは AWS What's New で毎日のように発表されていますが、「能動的に確認するのは面倒」、「知らない AWS のサービスや機能もあるし」と言い訳を並べるだけでチェックをサボりがちです。

私も面倒だから後回しにしていた人です。そこで「強制的に視界に入れて仕組みで解決し、ついでに AI に日本語で要約させて、ユースケースまで書かせよう！」と思い、[公式リポジトリ](https://github.com/aws-samples/whats-new-summary-notifier)を参考にして実装を行いました。実装した内容は以下のリポジトリで公開しています。

https://github.com/hot377/aws-whats-new-notifier

Terraform で AWS のリソースを管理している人にぜひ使っていただければ幸いです。

デプロイ手順や動作確認の手順はリポジトリの README に書いているので、この記事では、公式サンプルから変えたところと、その理由を紹介したいと思います。

## この記事で学べること

- RSS の新着を DynamoDB Streams で検知し、Bedrock で要約して Slack に通知する構成の全体像と、公式サンプルから変えた点
- DynamoDB の put と Streams の INSERT / MODIFY の違いを使った重複通知の防ぎ方
- Streams 起点の Lambda の失敗を DLQ とアラームで拾い、通知経路自体の障害に備えて Bot を分ける設計の考え方

## 想定読者

- AWS のアップデートを日本語で追いたいが、公式サンプル（CDK）ではなく Terraform で管理したい人


## アーキテクチャ図と処理の流れ

![](/images/2026-10-13/architecture.png)

1. EventBridge Scheduler が毎時 crawler を起動する
2. crawler が What's New の RSS を取得し、発行から 2 日以内の記事を DynamoDB に put する
3. DynamoDB Streams が notifier を起動する。notifier は INSERT のレコードだけを処理する
4. notifier が記事ページの本文を取得し、Bedrock の Claude で日本語要約を作って Slack に投稿する
5. 投稿に失敗し続けたレコードは SQS の DLQ に退避される
6. DLQ の滞留を CloudWatch アラームが検知し、alarm-notifier がアラート専用チャネルに通知する

Lambda は 3 つとも Python 3.13 / arm64 です。zip は 1 つを共用していて、handler の指定で処理を分けています。

実際に Slack に記事が投稿されるとこんな感じになります。

![](/images/2026-10-13/slack-post.png)

## 公式サンプルから変えたこと

RSS を DynamoDB に put して、Streams で通知用の Lambda を起動するという処理方式は、公式サンプルと同じです。また、今回は Slack だけに対応すれば良かったので、公式サンプルにある Microsoft Teams への通知、複数言語の要約などは実装しませんでした。

公式サンプルとの違いを表にまとめました。

| 観点 | aws-samples/whats-new-summary-notifier | 今回作ったもの |
| --- | --- | --- |
| IaC | AWS CDK（TypeScript） | Terraform |
| 定期実行 | EventBridge ルール（cron） | EventBridge Scheduler（`rate(1 hour)`） |
| Slack 連携 | Slack ワークフローの Webhook URL | Bot Token + `chat.postMessage` |
| 通知先 | Slack / Microsoft Teams | Slack のみ |
| Streams の設定 | NEW_IMAGE、batch size 1 | NEW_IMAGE、batch size 1（踏襲） |
| 失敗時の扱い | notifier が例外を握りつぶす（失敗した記事は通知されない） | リトライ + DLQ + CloudWatch アラーム + Slack 通知 |

公式リポジトリの列は、2026-10-11 時点のソース（`lib/whats-new-summary-notifier-stack.ts` と `lambda/notify-to-app/index.py`）を読んで確認しました。

## 設計のポイント

### 重複通知を DynamoDB Streams のイベント種別で防ぐ

毎時クロールするので、同じ記事を何度も取得してしまいます。そのため、通知済みの記事を再通知しないようにする必要があります。

ここは公式サンプルと同じ方式にしました。テーブルのパーティションキーを記事の URL にして、crawler は取得した記事を毎回そのまま put するようにしています。

```python
def build_item(entry, now):
    return {
        "url": entry["link"],
        "title": entry.get("title", ""),
        "description": entry.get("summary", ""),
        "published_at": time.strftime("%Y-%m-%dT%H:%M:%SZ", entry["published_parsed"]),
        "ttl": int(now) + TTL_DAYS * 86400,
    }
```

DynamoDB Streams のレコードには `eventName` があり、新しい項目の作成は `INSERT`、既存の項目の上書きは `MODIFY` になります。notifier は `INSERT` だけを処理するようにしています。

```python
for record in event.get("Records", []):
    if record.get("eventName") != "INSERT":
        continue
```

この方式だと、crawler 側で通知済みかどうかを確認する必要がありません。crawler の実行ロールに必要な DynamoDB の権限も `dynamodb:PutItem` だけです。

鮮度ウィンドウと TTL は別の値にしています。

| 設定 | 既定値 | 役割 |
| --- | --- | --- |
| 鮮度ウィンドウ | 2 日 | 発行からこの期間内の記事だけを put する。初回実行時に過去記事を大量に通知しないため |
| TTL | 30 日 | 通知済みの記録を残す期間。過ぎた項目は DynamoDB が自動で削除する |

TTL を鮮度ウィンドウより長くしているのは、再通知を防ぐためです。TTL で項目が消えたあとに同じ URL を put すると `INSERT` になりますが、その時点で記事は鮮度ウィンドウの外なので、crawler は put しません。

また、Streams のイベントソースマッピングは `LATEST` から読み始めます。マッピングができる前に crawler が動くと、そのとき put した記事は通知されずにテーブルに残ってしまい、次回以降は `MODIFY` になるので、通知されません。そのため、スケジュールはマッピングのあとに作成するようにしました。

```hcl
resource "aws_scheduler_schedule" "crawler" {
  name = "${var.name_prefix}-crawl-schedule-lambda"

  # notifier 側（Streams のマッピング）ができてから起動する
  depends_on = [aws_lambda_event_source_mapping.notifier]

  schedule_expression = "rate(1 hour)"
  # ...
}
```

:::message alert
Lambda のドキュメントには、マッピングの作成直後はポーリングの開始まで数分かかることがあり、`LATEST` だとその間のイベントを取りこぼすことがあると書かれています。そのため、作成直後の数分は取りこぼす可能性があります。
:::

### Slack 連携を Webhook ではなく Bot Token にした理由

公式サンプルは Slack ワークフローの Webhook に、タイトルや要約などの変数を渡して投稿していますが、今回は Bot Token を使って、`chat.postMessage` を呼ぶようにしました。

以前作った [AWS の重要通知を Slack に流す仕組み](https://zenn.dev/ho377/articles/2026-08-29-tech) が Bot Token を使っているので、同じ方式に揃えるためです。

また、`chat.postMessage` は投稿したメッセージの `ts` を返すので、スレッドに返信できます。アラーム通知では、この `ts` を使って AI 要約と解消報を第一報のスレッドに返信しています。1 つの事象を 1 スレッド内で解決できるので、個人的に気に入っている実装です。

なお、Token は Terraform では管理せず、SSM パラメータストアの SecureString に手動で登録して、Lambda が実行時に取得するようにしています。

### 要約とユースケースを書かせるプロンプト

知らない機能がどのように使われるのかを知りたかったので、要約だけでなく、ユースケースも書かせるようにしています。プロンプトだけを変更しやすくするために、Python や Terraform のコード内に埋め込まず、別ファイルにしました。これは、特定の拡張子のファイルの変更があった際に CI が走るリポジトリ向けの設計です。

```markdown
あなたは AWSの新機能を解説するアシスタントです。

Slack に投稿する内容を次の形式に従い日本語で出力してください

# 出力形式

*要約*
原文の内容を日本語で簡潔にまとめる（3〜6行）

*考えられるユースケース*
この新機能を使うことで、どのようなことが可能になるのかをユースケースを例示して記載する

# 注意

- Slack の mrkdwn 記法（*強調* や箇条書き）を使う。見出し記号 # は使わない
- 事実はイベント原文のみに基づき、原文にない情報は推測であることを明記する
- 前置きや締めの文は書かない
```

ユースケースは AI が考えたものなので、原文にない情報は推測であることを明記するように指示しています。


### 失敗を DLQ とアラームで拾う

新着が無い時間帯は何も投稿されません。そのため、通知が来ないだけでは、新着が無いのか、失敗しているのかが分かりません。なので、失敗したときは別で通知するようにしています。

失敗したときは、事象ごとに扱いを変えています。

| 事象 | 扱い |
| --- | --- |
| 記事ページの本文が取得できない | RSS の description で代用して続行する |
| Bedrock の要約が失敗する | 要約なし（タイトルとリンクだけ）で投稿する |
| Slack への投稿が失敗する | 例外を送出し、リトライと DLQ 退避に任せる |

要約に失敗しても、新着があったことは通知したいので、要約なしで投稿するようにしています。そのため、DLQ に入るのは、主に Slack へ投稿できなかったレコードです。

```python
def notify(article):
    body = fetch_article_body(article["url"]) or article["description"]
    try:
        summary = summarize(article, body)
    except Exception as error:
        # 要約は付加価値。新着があった事実の通知を優先し、要約なしで投稿する
        print(f"summarize failed for {article['url']}: {error}")
        summary = None
    post_to_slack(format_message(article, summary))
```

DynamoDB Streams のイベントソースマッピングは、既定ではリトライ回数が無制限（`MaximumRetryAttempts` が -1）で、レコードが期限切れになるまでリトライします。その間、同じシャードの後続のレコードは処理されません。Streams のレコードの保持期間は 24 時間なので、1 件失敗すると最大 1 日、通知が止まります。

そのため、リトライは最大 2 回にして、それでも失敗したレコードは SQS の DLQ に退避するようにしています。公式サンプルの notifier は例外を握りつぶすので、失敗した記事は通知されないままになります。

```hcl
resource "aws_lambda_event_source_mapping" "notifier" {
  event_source_arn  = aws_dynamodb_table.rss_history.stream_arn
  function_name     = aws_lambda_function.notifier.arn
  starting_position = "LATEST"

  batch_size = 1

  # リトライ最大2回。それでも失敗したレコードは DLQ へ退避する
  maximum_retry_attempts = 2

  destination_config {
    on_failure {
      destination_arn = aws_sqs_queue.dlq.arn
    }
  }
}
```

設定するときに気をつけた点です。

- Streams からの呼び出しは同期呼び出しなので、リトライと失敗時の送信先はイベントソースマッピングに書く。非同期呼び出し用の `aws_lambda_function_event_invoke_config` に書いても効かない
- DLQ への送信は関数の実行ロールの権限で行われるので、notifier の実行ロールに `sqs:SendMessage` が必要
- DLQ に入るのはレコード本体ではなく、シャード ID やシーケンス番号などのメタデータ。再通知したいときは、DynamoDB から該当の項目を削除して crawler を再実行する

リトライするので、Slack への投稿に成功したあとで失敗した場合は、同じ記事が重複して投稿される可能性があります。頻度は低いので、重複よりも取りこぼしを防ぐことを優先しています。

`batch_size = 1` は公式サンプルと同じです。1 記事ずつ処理するので、Bedrock の呼び出しが集中せず、投稿の順序も安定します。Streams はシャード単位で直列に関数を呼び出すので、実質 1 並列になります。予約同時実行数（`reserved_concurrent_executions`）は使っていません。発行したばかりのアカウントなどでは Lambda の同時実行数のクォータがデフォルトより低いことがあり、その場合は予約を確保できずに関数の作成が失敗するためです。

crawler はリトライしないようにしています。put は冪等で、失敗しても次の実行で同じ範囲を取得し直すためです。EventBridge Scheduler のリトライポリシーと、Lambda の非同期呼び出しのリトライは、どちらも 0 にしています。

DLQ の滞留は CloudWatch アラームで検知しています。メッセージが 1 件でも入ると ALARM になります。

```hcl
resource "aws_cloudwatch_metric_alarm" "messages_visible" {
  alarm_name        = "${var.queue_name}-messages-visible-${lower(var.priority)}"
  alarm_description = "${var.queue_name} にメッセージが滞留しています"

  namespace   = "AWS/SQS"
  metric_name = "ApproximateNumberOfMessagesVisible"
  dimensions = {
    QueueName = var.queue_name
  }

  statistic           = "Maximum"
  comparison_operator = "GreaterThanOrEqualToThreshold"
  threshold           = 1
  period              = 300
  evaluation_periods  = 1

  # メトリクスが欠落してもキューが空なだけなので ALARM にしない
  treat_missing_data = "notBreaching"
}
```

### アラーム通知の Bot を記事用と分ける

アラームの通知には `alarm_actions` と SNS を使っていません。アラームの状態変化イベントを EventBridge ルールで拾って、専用の Lambda（alarm-notifier）から Slack に投稿しています。これも、以前作った AWS の重要通知を Slack に流す仕組みと同じ処理方式にしたためです。拾うのは、ALARM への遷移と、ALARM から OK への遷移（解消）だけです。

```hcl
event_pattern = jsonencode({
  source        = ["aws.cloudwatch"]
  "detail-type" = ["CloudWatch Alarm State Change"]
  detail = {
    alarmName = [module.dlq_alarm.alarm_name]
    "$or" = [
      { state = { value = ["ALARM"] } },
      {
        state         = { value = ["OK"] }
        previousState = { value = ["ALARM"] }
      },
    ]
  }
})
```

OK への遷移に `previousState` の条件を付けているのは、アラーム作成直後の INSUFFICIENT_DATA から OK への遷移を、解消として通知しないようにするためです。

alarm-notifier は、以下の順で投稿します。

1. アラート専用チャネルに第一報を投稿する（アラーム名、状態、メトリクス、コンソールへのリンク）
2. Bedrock の Claude で要旨と推奨対応を作り、第一報のスレッドに返信する
3. 解消のイベントが届いたら、同じスレッドに解消報を返信する

解消報を同じスレッドに返信するために、アラーム名をキーにして第一報の `ts` を DynamoDB に保存しています。ALARM への遷移は、毎回新しいスレッドにしています。時間を置いて起きた別の障害が、古いスレッドに繋がらないようにするためです。

実際のスレッドはこんな感じになります。実験中のテスト通知なので、アラーム名などが少しリポジトリの実装と異なっています。

![](/images/2026-10-13/alarm-thread.png)

アラームを通知する関数は、notifier と分けています。notifier はストリームを直列に処理しているので、同じ関数にすると、notifier が詰まったときにアラームの通知も止まってしまうためです。

Slack の Bot とチャネルも、記事用と分けています。DLQ に入るのは、主に Slack へ投稿できなかったレコードです。原因が記事用 Bot の Token の失効だった場合、同じ Bot ではアラームも投稿できません。そのため、アラート用の Bot を別に用意しています。

alarm-notifier はリトライしないようにしています。第一報を投稿したあとで失敗した場合、リトライすると第一報が重複するためです。記事の通知は取りこぼしを防ぐことを優先しましたが、アラームの通知は重複しないことを優先しています。失敗したときは、失敗したことをアラートチャネルに投稿します。

注意点もあります。

- Slack への投稿自体が失敗した場合は、Slack に通知できない。アラート用 Bot の Token の失効や Slack 側の障害のときは、ログにしか残らない
- 通知は ALARM への遷移時に 1 回だけ。ALARM が続いている間にメッセージが増えても再通知されないので、通知が来たら DLQ が空に戻るところまで確認する

## 今後やってみたいこと

### 特定のトピックだけを投稿する

今は What's New の新着をすべて投稿しています。数が多いので、自分が使っているサービスや、興味のあるカテゴリだけを投稿できるようにしたいです。

RSS の各記事には `category` があり、サービス名やカテゴリが入っています。

```
general:products/aws-security-hub,marketing:marchitecture/security-identity-and-compliance
```

crawler で `category` を見て、対象の記事だけを put するようにすれば実現できそうです。

### URL が変わった記事の重複投稿を防ぐ

運用していると、同じタイトルの記事が 2 回投稿されることがありました。記事の URL があとから変更されたためです。

今の実装は URL をキーにして重複を判定しているので、URL が変わると別の記事として扱われて、`INSERT` になってしまいます。
クリティカルな問題ではありませんが、いずれ対応したいと思っています。

## まとめ

AWS What's New の新着を Bedrock の Claude で日本語要約して、Slack に通知する仕組みを Terraform で作りました。

- 重複通知は、URL をキーにした put と、Streams の `INSERT` / `MODIFY` の違いで防いでいる
- Streams から起動する Lambda は、リトライ回数と失敗時の送信先を設定しないと、1 件の失敗で最大 1 日止まる
- 新着が無いと何も投稿されないので、失敗は別の Bot とチャネルで通知している
